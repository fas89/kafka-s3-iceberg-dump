Default ingest engine: spark (fastest at every scale tested, 14,286 rps @ 200,000, flat memory). Default maintenance engine: Spark (only one with binpack + sort + zorder).

Implementation

Maven multi-module monorepo. mTLS Kafka → per-engine ingest → one Iceberg table per engine on MinIO via a shared Postgres JDBC catalog. Iceberg 1.10.2, Java 21, Docker Compose (base + one overlay per engine). Maintenance tuning is single-sourced in common/MaintenanceTuning.java.

engineingestmaintenance
flink ingest-only Flink job sibling flink-maintenance.jar container (PR #1 split) with RetryingTriggerLockFactory + DeleteOrphanFiles
spark Structured Streaming, partitioned by event_type in-job, native procedures (binpack / sort / zorder)
duckdb kafka-clients + DuckDB iceberg extension, micro-batched sibling flink-maintenance.jar container
connect iceberg-kafka-connect sink config, no Java sibling flink-maintenance.jar container

How it's measured

Java producer → mTLS Kafka → each engine writes <engine>_db.events on MinIO via a shared Postgres JDBC catalog. Scales: 50,000, 100,000, 200,000 events, clean stack per engine per scale. Timing from Iceberg snapshot timestamps (engine-agnostic); resources from docker stats sampled every 5 s across each engine's containers; correctness by polling rows until rows ≥ requested.

Caveats

  • Single host, Docker Desktop on macOS. Numbers are reproducible but don't generalize to multi-node production.
  • Engine-imposed latency floors: Flink commits on checkpoint (default 30 s); Connect commits on its interval-ms (default 5 s); DuckDB micro-batches every ~few-hundred-ms; Spark + Flink commit once at the end of a bounded run.
  • mTLS overhead is paid equally by every engine — comparison is fair, absolute rps would rise without mTLS.
