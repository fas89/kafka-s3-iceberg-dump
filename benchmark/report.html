Methodology

Workload: a Java producer publishes synthetic JSON events over mutual-TLS Kafka with the schema {id, event_type, user_id, amount, event_time}. Each engine consumes the same topic and writes its own Iceberg table (<engine>_db.events) on MinIO via a shared Postgres JDBC catalog, partitioned by event_type so the stream produces many small files for compaction.

Scales: 50,000, 100,000, 200,000 events per engine, each on a freshly torn-down stack.

Timing is derived from the Iceberg snapshot log (engine-agnostic source of truth, not from any engine's own metrics): startup_s = producer start → first append snapshot, ingest_s = producer start → last append snapshot, consume_drain_s = producer finish → last append. Throughput is requested / ingest_s.

Resources come from docker stats sampled every 5 s, summed across each engine's own containers (e.g. flink-jobmanager + flink-taskmanager for Flink). peak_mem_mb is the peak summed value; cpu_pct_avg is the mean.

Correctness is verified by polling the Iceberg table via the JDBC catalog until rows ≥ requested; the row count exact column is the explicit verdict.

Schema handling

This branch does not add a central schema-mapping layer; each engine implements its own JSON → Iceberg conversion for the fixed 5-field event schema. The repo dedupes this in 6 spots:

wheremechanism
producer/EventProducer.javaJava Map + Jackson JSON
engine-flink/FlinkIngestJob.javaIceberg Schema + RowType
engine-flink/JsonToRowData.javahand-written JsonNode → GenericRowData
engine-spark/SparkIngestJob.javaSpark StructType + CREATE TABLE DDL
engine-duckdb/DuckDbIngestJob.javaDuckDB SQL DDL + PreparedStatement
engines/connect/iceberg-sink.jsonJsonConverter + auto-create-enabled + evolve-schema-enabled

Connect differentiator: with evolve-schema-enabled: true, Connect can add columns on the fly when new JSON keys appear. The other three engines have compile-time-fixed schemas and silently drop unknown fields. The throughput numbers in this report don't capture that flexibility edge.

Compaction strategy comparison

Identical many-small-files Iceberg tables compacted with each strategy via Spark's rewrite_data_files procedure. Output size is essentially identical; the difference is wall-clock time and the data-locality benefit on later reads (not measured here).

metricbinpacksortzorder
rows80,00080,00080,000
files before646464

rewritten bytes856,129856,186856,613

Strategy guidance: pick binpack when you only need to coalesce small files; pick sort if your reads filter on one column (typically event_time); pick zorder if your reads filter on two correlated columns (e.g. user_id + event_time). The cost ranking on compaction time is typically binpack < sort < zorder.

Verdict & recommendation

Your proposal evaluated

You suggested DuckDB or Kafka Connect for ingest, with Spark or Flink running maintenance on the side. The pattern is supported by the repo (docker-compose overlays for either DuckDB or Connect + a standalone maintenance container, swappable between Flink-based and docker-compose.maintenance-spark.yml Spark-based) — but the measured data argues for a small revision: between DuckDB and Connect, DuckDB is the right ingest engine. The bigger surprise is that Spark beats both at every scale, so unless single-process simplicity or fleet-management is a hard requirement, Spark is the default.

  • Between DuckDB and Connect, DuckDB wins — at 200,000 events: DuckDB 6,250 rps vs Connect 2,128 rps. DuckDB also wins memory (516 MB vs 1,404 MB), at the cost of being single-node.
  • But Spark beats both — Spark 13,333 rps at 200,000, with 788 MB and CPU efficiency comparable to DuckDB. If you don't need DuckDB's single-process trait or Connect's fleet management, Spark is the default ingest engine and also the maintenance engine.
  • Maintenance engine — prefer Spark. Spark's rewrite_data_files procedure supports binpack, sort and zorder; Flink's table-maintenance API only does binpack. The Spark maintenance container also stays small (no streaming job, just a batch trigger), so the memory cost vs Flink-based maintenance is modest.

Top-line: the data inverts the small-scale intuition. Spark wins raw throughput at every scale tested (13,333 rps at 200,000, with effectively flat memory). Default ingest engine is therefore Spark. Use DuckDB only when memory or single-process simplicity matters more than speed (516 MB at 200,000, leanest by far). Use Kafka Connect only when you need a fleet-managed REST-configured worker (slowest measured, 2,128 rps at 200,000). Spark is also the right side maintenance engine in every case — the only one that ships binpack + sort + zorder.

Caveats & threats to validity

  • Single host. All four engines run on one machine, sharing CPU and disk I/O. Numbers do not generalize to multi-node deployments.
  • Docker Desktop on macOS. Container networking and disk I/O have an overhead Linux hosts don't. Treat absolute numbers as upper bounds for relative comparison only.
  • mTLS overhead is real but constant. Every engine pays the same handshake / encryption cost, so the comparison is fair, but throughput numbers would rise without mTLS.
  • Connect's commit interval (iceberg.control.commit.interval-ms = 5000) bounds its commit cadence. Lowering it improves freshness but increases commit-overhead. Defaults shipped.
  • Flink's 30 s checkpoint interval is a latency floor — Iceberg commits on checkpoint, so startup_s never goes below ~22 s no matter the load.
  • DuckDB writes in micro-batches (10 commits per run by default); other engines often commit once at the end. That's why drain_s is non-zero for DuckDB and ~0 for the others.
  • Demo defaults. MinIO admin/password, Postgres iceberg/iceberg, keystore changeit — do not use in production.

Reproducibility

From a clean clone:

  • ./certs/generate-certs.sh — one-time, generates the local-CA mTLS material under certs/
  • ./mvnw -DskipTests package — (optional) builds every module's fat jar; the Docker builder service does this inside the container otherwise
  • benchmark/run-scales.sh 50000 100000 200000 — runs all four engines on each scale, on a clean stack per engine, and stashes per-engine JSON results into benchmark/results/scale-<N>/
  • benchmark/compaction.sh 80000 — (optional) binpack / sort / zorder compaction comparison
  • python3 benchmark/report.py — renders this HTML from the raw JSON
